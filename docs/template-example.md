## 핵심 개념

### 클로저는 "외부 변수에 접근하는 것"이 아니다

처음엔 클로저를 "내부 함수가 외부 함수의 변수에 접근할 수 있는 것"으로 이해했다. 틀린 건 아닌데, 이렇게 이해하면 클로저가 왜 필요한지가 설명이 안 된다.

더 정확한 관점은 이렇다. 함수가 실행될 때 JavaScript는 그 함수가 **선언된 시점의 스코프를 함수와 함께 보존**한다. 함수가 어디서 호출되든 상관없이. 클로저는 함수가 자신이 태어난 환경을 기억하는 메커니즘이다.

이 차이가 중요한 이유는, 클로저가 단순한 접근 권한이 아니라 **상태를 캡슐화하는 수단**이기 때문이다. 외부에서 직접 건드릴 수 없는 변수를, 함수를 통해서만 읽고 바꿀 수 있게 만드는 것. 이게 클로저가 실제로 쓰이는 이유다.

### 스코프 체인은 선언 위치가 결정한다

JavaScript는 함수가 **선언된 위치**를 기준으로 스코프를 결정한다(렉시컬 스코프). 호출된 위치가 아니다. 이 원칙이 클로저를 가능하게 한다.

```js
function outer() {
  const message = 'hello';
  return function inner() {
    console.log(message); // outer가 끝난 뒤에도 접근 가능
  };
}

const greet = outer();
greet(); // 'hello'
```

`outer()`가 실행을 마쳤어도 `inner`는 `message`를 기억한다. `inner`가 선언된 시점에 `message`가 있던 스코프가 함께 보존되기 때문이다.

## 챌린지 접근 방식

### Challenge 1 — makeCounter() 구현

독립적인 카운터를 여러 개 만들 수 있어야 했다. 각 카운터는 서로의 상태에 영향을 주지 않아야 한다.

처음엔 전역 변수로 해결하려 했다. `let count = 0`을 두고 `increment()` 함수를 만들면 되는 거 아닌가? 금방 문제가 보였다. 카운터가 두 개 필요하면 변수도 두 개, 함수도 두 개 만들어야 한다. 카운터가 열 개라면?

클로저를 쓰면 `makeCounter()`를 호출할 때마다 독립적인 `count` 변수가 생긴다는 걸 깨달았다.

```js
function makeCounter() {
  let count = 0;
  return {
    increment() { count++; },
    decrement() { count--; },
    value()     { return count; }
  };
}

const counter1 = makeCounter();
const counter2 = makeCounter();

counter1.increment();
counter1.increment();
counter2.increment();

counter1.value(); // 2
counter2.value(); // 1 — 서로 독립적
```

`count`는 외부에서 직접 바꿀 수 없다. 반환된 메서드들을 통해서만 접근할 수 있다. 이게 클로저로 상태를 캡슐화한다는 말의 의미였다.

## 처음엔 틀렸다

루프 안에서 클로저를 쓸 때 `var`와 `let`의 동작이 다를 거라는 건 알았다. 그런데 왜 다른지는 잘못 이해하고 있었다.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// 예상: 0, 1, 2
// 실제: 3, 3, 3
```

처음엔 "타이머가 늦게 실행되면서 `i`가 이미 바뀐 것"이라고 생각했다. 절반은 맞는데 핵심을 빗나갔다.

정확한 이유는 `var`로 선언한 `i`가 루프 블록이 아닌 **함수 스코프(또는 전역 스코프)에 하나만 존재**하기 때문이다. 세 개의 콜백은 각자 다른 `i`를 캡처한 게 아니라, 같은 `i` 하나를 공유하고 있다. 루프가 끝날 때 그 하나의 `i`는 `3`이 되어 있고, 세 콜백 모두 같은 값을 출력한다.

`let`은 루프 반복마다 **새로운 스코프의 새로운 `i`를 만든다.** 그래서 세 콜백이 각자 독립적인 `i`를 캡처하게 된다.

이 차이를 이해하고 나서야 "클로저는 값이 아니라 변수를 캡처한다"는 말이 진짜로 와닿았다.

## 더 파고든 것

> 💬 **AI 대화 인사이트**
>
> **처음에 흐릿했던 부분:** JavaScript는 왜 호출 위치가 아닌 선언 위치를 기준으로 스코프를 결정하는가? 반대로 설계하면 어떤 문제가 생기는가?
>
> **대화를 통해 깨달은 것:** 호출 위치 기준(동적 스코프)으로 동작하면 함수의 동작을 예측하기가 훨씬 어렵다. 같은 함수를 어디서 호출하느냐에 따라 결과가 달라지기 때문이다. 선언 위치 기준(렉시컬 스코프)이면 코드를 읽을 때 함수가 어떤 변수에 접근하는지 실행 전에 알 수 있다. 클로저는 이 렉시컬 스코프 원칙의 자연스러운 결과물이다. 별도로 설계된 기능이 아니라, 스코프 규칙을 일관되게 적용한 결과다.

이 관점이 바뀌고 나서 클로저를 바라보는 시각이 달라졌다. 클로저를 "특별한 기능"으로 외우는 게 아니라, "JavaScript가 스코프를 어떻게 다루는가"를 이해하면 자연스럽게 따라오는 개념이 된다.

## 실무 연결

React의 `useState`가 클로저로 동작한다. 컴포넌트 함수는 렌더링마다 다시 실행되지만, 상태 값은 유지된다. `useState`가 반환하는 setter 함수가 이전 렌더링의 상태를 기억하고 있기 때문이다.

이벤트 핸들러도 마찬가지다. 버튼에 붙인 핸들러는 컴포넌트가 처음 마운트됐을 때의 스코프를 기억한다. React에서 `useCallback`이 필요한 이유, 의존성 배열(dependency array)이 존재하는 이유가 바로 이 클로저 동작과 연결된다.

Node.js의 모듈 시스템도 클로저 원리로 외부에서 접근할 수 없는 프라이빗 상태를 만든다.
