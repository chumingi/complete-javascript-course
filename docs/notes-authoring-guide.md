# CLAUDE 대화 설계 — notes.md 작성 가이드

> **관점: 포트폴리오**
> 이 가이드는 섹션별 학습 내용을 포트폴리오 수준의 기록으로 남기기 위한 Claude와의 대화 설계를 기술한다.
> 특정 언어나 기술 스택에 종속되지 않으며, 모든 섹션에 동일하게 적용된다.

---

## 목적

강의를 듣는 것과 이해하는 것은 다르다. 이해했다는 것을 증명하는 가장 강력한 방법은
**왜 이렇게 설계됐는지, 언제 쓰지 않는지, 처음에 뭘 오해했는지**를 기록하는 것이다.

notes.md는 학습 일지가 아니라 **사고의 흔적**이다.
면접관에게 보여줄 때, "문법을 외운 사람"이 아닌 "언어를 이해하는 사람"으로 읽혀야 한다.

---

## 두 가지 운영 모드

### Mode A — 섹션 종료 후 리뷰

섹션을 완전히 수강한 후 notes.md를 작성하는 경우.

**첫 번째 대화 세션:**
1. Claude가 해당 섹션의 코드 파일 전체를 파악한다
2. 이 섹션에서 다루는 전체 개념 목록을 notes.md 상단에 추가한다
3. 개념 간 의존성과 학습 흐름을 고려하여 진행 순서를 제안한다
4. 순서를 확정한 뒤 1회차 리뷰를 바로 시작한다

**이후 대화 세션:**
- 한 세션 = 한 개념 (확정된 목록에서 순서대로)
- 세션 시작 시 어느 개념을 다룰지 명시한다
- 세션 종료 시 Claude가 대화에서 나온 핵심 인사이트를 요약해서 제시한다
- 사용자는 요약을 참고하여 notes.md 항목을 직접 작성한다

---

### Mode B — 섹션 진행 중 실시간 작성

강의를 들으면서 그때그때 notes.md를 작성하는 경우.

**매 대화 세션 시작 시:**
1. 오늘 배운 개념을 말한다
2. Claude가 notes.md 상단의 개념 목록에 해당 개념을 추가한다
3. 대화를 통해 개념을 심화 탐구한다
4. 세션 종료 시 Claude가 대화에서 나온 핵심 인사이트를 요약해서 제시한다
5. 사용자는 요약을 참고하여 notes.md 항목을 직접 작성한다

**누적 관리:**
- 아직 다루지 않은 개념이 목록에 쌓인다
- 섹션이 끝난 후 빠진 개념이 있으면 Mode A 방식으로 보완한다

---

## 개념 진행 순서 설계 원칙

진행 순서는 강의 순서를 따르는 것이 기본이지만, 아래 기준으로 묶거나 재배치할 수 있다.

| 기준 | 설명 |
|------|------|
| **의존성** | A를 이해해야 B가 이해되는 경우, A를 먼저 |
| **대비** | 비슷해 보이지만 다른 두 개념은 같은 세션에서 비교 탐구 |
| **복잡도** | 기초 개념 → 응용 개념 순서로 |
| **실무 밀도** | 실무에서 자주 쓰이는 개념에 더 많은 시간을 |

> 예시: Spread와 Rest는 문법이 같고(`...`) 역할이 반대이므로 같은 세션에서 대비하여 탐구한다.
> 예시: Short Circuit, `??`, 논리 할당 연산자는 모두 "조건을 간결하게 쓰는 방법"이므로 함께 묶는다.

## 대화 흐름 (개념 1개당)

### 1단계 — 워밍업

> Claude: "이 개념, 한 문장으로 설명해봐."

현재 이해 수준을 파악하기 위한 질문. 정답/오답 판정이 아니다.
대답의 내용을 보고 어느 깊이에서 대화를 시작할지 조정한다.

---

### 2단계 — 설계 의도

> Claude: "이 개념이 없었다면 어떻게 했을까? 왜 만들어졌을까?"

가장 중요한 단계. 문법 암기가 아닌 **설계 의도 이해**가 목표다.
포트폴리오에서 이 부분이 차별점이 된다.

---

### 3단계 — 스스로 추론 유도

흐릿한 부분이 있으면 Claude가 2~3개의 선택지를 제시한다.
바로 답을 주지 않고, 사용자가 직접 추론하도록 유도한다.

```
Claude: "다음 중 어떻게 생각해?
  A) ...
  B) ...
  C) ..."
```

---

### 4단계 — 혼동 지점

이 개념에서 많이 오해하거나 헷갈리는 부분을 Claude가 짚는다.
사용자가 이 함정에 빠진 적이 있으면 → **"처음엔 틀렸다" 섹션의 소재**가 된다.
실제로 오해한 적이 없으면 억지로 만들지 않는다.

---

### 5단계 — 경계선

> Claude: "이 개념을 쓰면 안 되는 상황은?"

"언제 쓰는가"만큼 "언제 쓰지 않는가"도 이해를 드러낸다.
이 질문에 답할 수 있는 사람은 문법을 아는 게 아니라 개념을 이해하는 것이다.

---

### 6단계 — 실무 연결

React / Node.js / 브라우저 API / 외부 API 맥락에서 이 개념이 어디에 등장하는지.

- 억지 연결 금지 — 실제로 쓰이는 맥락만 언급한다
- "이런 라이브러리의 이런 패턴이 이 개념으로 동작한다" 수준이 이상적
- 연결되는 맥락이 없으면 이 단계를 생략한다

---

### 7단계 — 정리

> Claude: "지금 대화에서 가장 중요한 인사이트 한 줄로?"

이 한 줄이 notes.md 항목의 핵심 문장이 된다.
대화를 통해 스스로 도달한 결론을 직접 말하게 하는 것이 목표다.

---

## 대화 깊이 기준

| 레이어 | 핵심 질문 | 포트폴리오 가치 |
|--------|-----------|----------------|
| 문법 | 어떻게 쓰나? | 낮음 — 코드에 이미 드러나 있음 |
| 의도 | 왜 이렇게 설계됐나? | 높음 |
| 경계 | 언제 쓰면 안 되나? | 매우 높음 |
| 실무 | 실제 코드베이스 어디에 등장하나? | 매우 높음 |
| 오류 | 처음에 뭘 오해했고 어떻게 바뀌었나? | 최고 — 진정성을 증명 |

문법 레이어는 코드에 이미 드러나 있으므로 대화에서 빠르게 지나간다.
오류 레이어가 있는 항목이 notes.md에서 가장 강력한 섹션이 된다.

## notes.md 관리 방식

> notes.md는 학습 과정의 개인 기록이며 외부에 공개되지 않는다 (`.gitignore` 처리).
> README.md 작성의 원재료가 되므로, 반드시 사용자가 직접 작성한다.

### 개념 목록

파일 상단에 개념 목록을 순서 있는 리스트로 유지한다.
완료된 개념은 항목 옆에 날짜를 추가하고, 미완료 항목은 날짜 없이 남긴다.

```markdown
## 개념 목록

1. Array Destructuring — 2025-xx-xx
2. Object Destructuring — 2025-xx-xx
3. Spread Operator
4. Rest Pattern
5. Short Circuiting & Nullish Coalescing
...
```

체크박스(`- [ ]`) 방식을 사용하지 않는다.
완료/미완료 상태보다 **탐구의 흔적**이 더 중요하기 때문이다.

---

### 항목 작성 원칙

각 개념의 notes.md 항목은 대화가 모두 끝난 후 사용자가 직접 작성한다.
세션 종료 시 Claude가 제시하는 인사이트 요약은 참고 자료일 뿐, 그대로 옮기지 않는다.
쓰는 행위 자체가 학습이기 때문이다 — 내 언어로 재구성하는 과정에서 이해의 빈 곳이 드러난다.

**포함해야 할 것:**
- 내가 이해한 방식으로 쓴 설명 (강의 내용 복사 금지)
- 이 개념이 왜 필요한가 (설계 의도)
- 언제 쓰지 않는가 (경계) — 있을 경우
- 실무 맥락과 코드 예시 — 연결이 자연스러운 경우에만
- AI 대화 인사이트 블록 — 흐릿했던 부분과 깨달은 것

**포함하지 않을 것:**
- 강의 내용 그대로 옮긴 설명
- 모든 API/메소드 나열 (notes.md는 레퍼런스 문서가 아님)
- 실제로 깨달음이 없었는데 억지로 쓴 인사이트

---

### AI 대화 인사이트 블록 형식

```markdown
> 💬 **AI 대화 인사이트**
>
> **처음에 흐릿했던 부분:** ...
>
> **대화를 통해 깨달은 것:** ...
```

이 블록은 대화에서 실제로 흐릿했던 부분이 있을 때만 작성한다.
없으면 블록 자체를 생략한다.

## 포트폴리오 관점 — 면접관에게 보여줄 것

이 프로젝트를 보는 면접관에게 전달하고 싶은 메시지:

> **"문법을 외운 사람이 아니라, 왜 이렇게 설계됐는지를 이해하는 사람"**

이를 위해 각 notes.md 항목이 아래 세 가지 중 적어도 하나를 포함해야 한다:

| 요소 | 예시 |
|------|------|
| **설계 의도** | "이 개념은 X 문제를 해결하기 위해 존재한다" |
| **경계 인식** | "이 상황에서는 쓰지 않는다. 왜냐하면..." |
| **오류와 교정** | "처음엔 이렇게 이해했다가 이런 이유로 바뀌었다" |

세 번째 요소가 가장 강력하다.
오해하고 교정한 기록은 진정성과 학습 깊이를 동시에 증명하기 때문이다.

---

## 섹션 종료 후 README 작성

모든 개념의 notes.md 항목이 완성되면 README.md를 작성한다.

README는 notes.md의 요약이 아니다.
**이 섹션에서 가장 중요한 것들의 선별된 기록**이다.

- `/docs/template.md`의 구조를 따른다
- notes.md에서 가장 인상 깊었던 개념 1~3개만 선별한다
- "처음엔 틀렸다" 섹션이 있으면 반드시 포함한다 — 이 섹션이 있는 README는 깊이가 다르게 읽힌다
- 모든 개념을 다 담으려 하지 않는다. 적게 써도 밀도 있는 게 낫다
